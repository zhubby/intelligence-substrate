# 从业务目标到可审阅需求稿

落实已批准规划的需求入口：用户可以只创建业务目标，在澄清后由人或模型整理需求稿，逐项审阅并采纳，再单独批准基线。当前增量只完成这一已有流程，不将本机模型样本作为真实需求质量或P3证据。

## 权威状态

- goals.create 省略 criteria 时保存空数组；明确传入的标准仍按原规则校验。goals.approve 强制至少一项有效标准。已有含标准流程继续兼容。
- requirement_proposal 是不可变原稿，内容为 outcome（12000字节）、brief（16000字节，用户/场景/范围与排除项）、1–100项 text/method 标准。严格字段、规范化重复拒绝，ID由服务端分配；不允许模型修改目标渠道、预算、权限或答案。
- requirements.propose 允许人类/Agent的产品、分析、设计、架构和开发角色，拒绝Worker；要求当前未批准版本、明确版本和幂等键。必须先回答当前问题。
- 输入快照包含业务目标、原验收、目标渠道、预算、来源、当前完整已答澄清及有效项目知识；保存规范JSON和SHA256。最多200份稿/目标。
- requirements.apply 仅人类产品/负责人可用。提交原稿ID、期望需求版本、幂等键、原因及完整审阅内容。原稿、输入摘要与当前上下文必须一致；允许人编辑内容，保留采用内容及摘要、采纳人/时间、旧/新版本和变化原因。
- 采纳原子创建新需求版本，复用现有失效逻辑，重新等待基线批准；任何未决新问题或知识变化使旧稿不可采纳。原问题保留历史，本次明确采纳的已答快照复制为新版本记录，保留原确认人/时间和来源批次/版本。单独批准后规划和Worker读取新基线及答复。
- 重复同键返回原结果；改变载荷409。权限在事务中重新检查；审计失败全量回滚。两份稿并发采纳只能一个成功。

## 受控模型

- POST /api/v1/requirements/generate 仅人类产品/负责人，使用 requirement_generation 意图；私有 chat 路径扩展为可信的两种需求生成类型，公开JSON字段不能选择草稿模式。
- 先保存精确输入与幂等意图，再按现有项目策略/预算/次数/速率限制调用；费用带 requirementRequestId。完整结果、settled费用、精确输入与当前权限确认后原子保存稿与完成审计。
- running/failed同键不重发；成功重放原稿。格式错误、未知结果、撤权、版本/答复/知识变化只记录失败和费用，不能写入稿、改动基线或隐藏费用。无自动重试或免费退款。
- 仅返回JSON内容；超界字段、伪造证据/答案/批准被结构拒绝。模型语义正确性由人工审阅与后续独立验证判断。

## 工作台

需求页显示当前需求说明、可整理/人工起草、稿件来源/版本/费用记录、当前与拟议验收对照。独立对话框支持编辑业务结果、需求说明、标准与方法；采纳前必须填写原因。明确说明会创建新版本并重新等待批准。有未决问题时不能整理/采纳。旧稿仍可查看，不能将旧上下文用于当前版本。

## 验证与保留

真实服务测试覆盖原始目标、空标准门禁、快照失效、人工答复迁移、幂等、权限/撤权、审计回滚、模型费用与迟到结果。专用PostgreSQL验证并发采纳和非空幂等历史归档恢复。HTTP/MCP和真实浏览器桌面/手机覆盖完整原始目标→问题→答复→模型稿→人工编辑→采纳→批准路径及失败。
