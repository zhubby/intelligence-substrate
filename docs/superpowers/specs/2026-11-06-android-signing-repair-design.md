# Android 签名包的受控修复闭环

## 范围与依据

在已批准总体产品设计和 016 受控签名能力之上，补齐独立质量验证失败后的修复、无签名构建、重新签名和复验。当前 `afterRepair` 只能复用含 command/outputPath 的构建任务；签名任务没有这两个字段，导致链路阻塞。

继续在当前功能分支主线程执行，不使用子 Agent，不暂存、提交或推送。保持原预览、Docker、AVD、既有输出及 Git 索引完整。临时测试身份只用于本机验证，不代表企业证书、真机验收、商店发布或生产交付。

## 产品行为

独立质量策略绑定的已确认签名包失败后，平台按已批准的开发配方创建修复任务。修复提交通过可信源码校验后，平台创建新的无签名构建、新的签名转换和原策略的复验任务。每轮操作有新的任务 ID 和签名 operationKey，不复用原签名意图。每个缺陷最多两轮，结果不明确、权限/策略/来源变化或预算不足时阻塞并记录原因。

自动修复只接受当前有效的质量策略、当前需求与方案、准确失败制品以及原批准构建与签名配方。人工临时测试或来源不完整时保留失败记录并要求人工处理，不能由失败事件扩大签名权限。

## 权威记录与校验

缺陷持久化每轮 `androidSigningRepairs` 记录，关联失败测试与执行、失败包、原构建/签名任务及摘要、质量策略和修复任务。修复完成后增加独立的 continuation，关联准确修复执行/提交、无签名构建、签名任务和复验任务及其配方摘要。两轮记录都保留。

生成任务使用外部方案不可写入的 `signingRepairId`。记录与配方摘要用于一致性验证，不是密码学授权签名；访问控制仍由控制面执行。校验领取、续租、源码/制品上传、完成、签名输入和签后制品使用。受控修复链拒绝通用拆分和重排，调整配方需要新批准工作。任务配方摘要仅排除 attempts/reason、领取时生成的 sourceBinding/sourceConflict/signingInput，以及从可信来源推导的源码和质量调度字段；源码另按权威失败包/修复执行验证。

原批准配方在首次派生时与方案任务核对，后续持续检查其摘要及方案任务摘要。保护原证书、运行平台、角色、目标、构建命令、输出路径和质量策略，既有普通修复路径保持兼容。签名失败/租约过期继续进入人工核对，不会触发自动修复或重签。

## 验收

1. 控制面和真实 Worker/HTTP/Git 测试覆盖失败、修复、无签名重建、新签名、独立复验和缺陷关闭。
2. 两轮上限，质量策略撤销、配方/证书/源码/记录漂移、伪造字段、重复完成和未知签名状态不能越界。
3. PostgreSQL 并发领取、重复完成、归档恢复保留新记录；普通修复和现有回归通过。
4. 本机 Flutter release APK 的真实 UI 缺陷由模拟器独立检查发现；确定性源码修复、重建与临时证书签名后，独立安装相同最终 APK 并通过离线复验。固定命令用例不宣称模型自主推理。
5. 真机、在线业务、企业证书、商店及 Apple 许可的未完成状态如实保留；整个 P3 不标为完成。
