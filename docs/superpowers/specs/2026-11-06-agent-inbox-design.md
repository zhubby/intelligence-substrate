# Agent 双向协作上下文

日期：2026-11-06。属于已批准产品规划中的结构化协作、持久化与恢复能力，继续在当前工作分支实施；不新增外部通信协议或发布授权。

## 现有缺口与目标

Agent 可以调用 messages.send，但执行循环不读取回复。通用 claim/ack 把消息交给节点身份，缺少工作项与需求版本绑定；进程失联后无法证明下一次执行仍拥有这些上下文。本增量将消息交付给持久工作项上下文，支持真实 Worker 在执行之间双向交换，并把上下文带到同一任务重试。消息不能视为已理解、已执行、质量通过或人工批准。

## 契约

- messages.send 保留原字段；有 goalId 时由控制面写入当前 requirementRevision。Worker 必须附 runId/leaseToken，只能代表当前有效执行在自己的目标中发送。已停用节点、过期/取消/已接管执行及旧基线拒绝发送。
- 收件人必须是项目内有效成员、启用 Worker 或有效项目 Agent token 身份。causationId 若非空，必须指向相同项目、目标与需求版本的消息。payload 必须是对象、序列化最多 8 KiB；拒绝密钥。发送者、版本、原执行均从认证及权威状态推导。
- 新命令 messages.receive {runId,leaseToken} 仅供 Worker，使用当前租约校验。返回 message-inbox，其 data.items 为持久 message_receipt，data.deferred 表示达到上下文上限而仍有未接收消息。首次接收时在同一事务记录 receipt 并将原消息变为 delivered；receipt 明确表示进入任务上下文。
- 只接收发给当前 Worker、相同 goal 和当前 requirementRevision 的 pending 或已过期 leased 消息。未过期旧 claim 不抢占，超过投递次数的消息保留 blocked。全项目消息和旧版本消息不自动注入任务。
- 有目标的 Worker 消息绑定 recipientTaskId；省略时从该目标唯一活动执行推导。平台已限制单节点一个活动任务，显式收件工作项用于给后续工作项排队，当前工作项不得误收。
- receipt 绑定 taskId、planId、requirementRevision、首次 run/Worker 和不含租约令牌的消息快照。同一任务每个消息只有一份 receipt；新租约/新 Worker 在同一有效任务上可以恢复已接收记录。别的任务或旧方案不能借用。
- 单一工作项最多 32 条、序列化 64 KiB 的持久协作上下文；达到上限仍有匹配消息时保留未收消息、返回 deferred，Worker 明确阻塞并释放执行。大上下文需要负责人调整工作项，而不是截断或假装全部接收。
- 空轮询及原样历史读取不追加审计；首次接收记录审计。通用 claim/ack 对人类及外部 Agent 保留；Worker 使用当前执行绑定的 receive，不能用旧 claim/ack 绕过绑定。

## Agent 与工作台

Agent 在每次模型请求前接收消息。每个 receipt 在一次模型循环中只注入一次，类型、来源、目标、版本、因果关系作为不可信 user 上下文提供；模型输出及消息都没有系统指令权限。读取或模型失败后 receipt 保留，后续执行可以恢复。发送 action 保留租约字段。

接受模型 finish 前再收件；如模型响应期间收到新内容，继续循环。最后一次检查之后仍可能到达消息，不能声称原子排空或保证理解。尚无自动等待、唤醒或模型步骤检查点；缺少回复时阻塞，负责人后续重试同任务恢复上下文。固定 command 任务不注入模型协作上下文。

工作台在既有工作项详情展示收到的协作上下文、原消息、发送者、首次接收执行与版本，便于工程师核对。收件记录不展示凭据。

## 验收与边界

真实 SQL/HTTP/Worker 验证：两节点发送/接收/回复、执行中的新消息进入后续模型步骤、同任务重试换节点仍有上下文、过期/跨目标/旧基线/伪造来源拒绝、并发接收唯一记录、事务失败无半份交付、容量不截断及 backup/restore 保留。桌面/手机核对呈现、键盘与滚动。模型上游使用确定性提供方，不冒充真实模型通过。
