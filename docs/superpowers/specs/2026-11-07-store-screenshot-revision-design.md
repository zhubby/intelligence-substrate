# App Store 截图资料修订

## 目标与授权

延续已批准产品规划中的渠道拒审与补充材料闭环。当前同构建资料修订只允许文字/HTTPS，截图更换被明确拒绝。本增量补齐独立批准的截图/文字修订、异步图片处理、原版本重新提审及准确资料的独立发布验收。完整多端正式交付目标保持不变。

## 设计与边界

- 人工拒审决定增加 `store-media`，原 `store-text` 继续只允许文字。截图修订在 spec、批准、任务、目标、查询和发布器请求中绑定 `materialScope:"screenshots"`；旧文字对象/请求省略此字段，摘要保持兼容。提案人和资料作者不能自批。权限、需求、方案、质量和当前资料来源每步复核。
- 保留原 IPA、提交、候选 binding、构建、版本、submission/item 与其他渠道。语言集合及顺序保持；允许按批准清单变更截图字节、数量、规格和展示顺序，以及文字/链接。私有图片仍由管理员在固定 profile 下安装，不引入任务选择的路径、凭据或 Apple ID。
- 先检查准确原文字、图片、展示顺序、版本和拒审项，再原子预约唯一后继及 app 写权限。使用现有有界 PNG/JPEG、摘要/大小、目录、规格目录和上传 host 检查。未改变的准确图片可复用原 image ID；改变图片使用新预约和准确上传字节。
- 新图片未就绪时保存 `material_images_processing` 与完整 image ID，返回 `processing`，释放平台 Worker 租约，保留发布器 app 预约。只读 status 校验原展示项和新图片；全部就绪后按原批准通过显式 continuation provider 继续。并发继续只有一次 CAS 可取得写权限。
- 使用 Apple 公开 DELETE placement、POST placement 和 ordering request 接口；不调用不存在的 PATCH placement，不删除共享库图片。仅删除原准确展示项，每步持久写前意图并读取剩余集合；新展示项与顺序独立读回后才 resolve 原 item、重新 submit。新图处理中绝不删除旧展示项。
- 未知写结果保持 pending/待核对，不自动 retry 或换 key。已接受最终 resubmit 可沿用管理员只读恢复；中间图片/展示项不确定结果不自动补写。恢复不等于批准或独立发布验收。
- 当前资料 digest/publication binding 才能形成发布验收，旧资料证据不能关闭截图修订。审核等待、已发布和已验收分别记录。UI 展示范围与图片处理状态，原文字流程保持。

## 验证

先在现有控制面和发布器观察截图用例失败，再实现。真实本机 TLS、PNG 字节、SQLite 日志验证两轮、就绪等待、准确删除/重排、并发继续、未知响应、漂移/撤权和只读恢复；HTTP Worker 证明传递准确范围且不重传 IPA。PostgreSQL 覆盖唯一领取、重放及跨数据库恢复。浏览器在桌面/手机验证独立提案/批准/派发和真实阶段显示。完整 Go race、Python、前端构建/格式及输出独立读回是完成门槛。

这些 Apple 回执仍是协议替身，不证明真实审核、签名、真机或生产。Apple SDK 仍需用户本人接受许可。主线程执行；不派子 Agent、不调用付费模型、不提交/推送、不改暂存区，不操作真实渠道。保留764原源码的无关内容、343旧输出、18080预览/dist、Docker、AVD 和钥匙串。证据根 `work/screenshot-revision-yyimwekb`。
