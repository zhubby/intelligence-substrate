# 渠道拒审回流与修复交付

## 授权与范围

执行用户已批准的完整研发交付规划中“拒审或验证失败 → 修复或补充材料 → 开发 → 新候选 → 重新批准 → 渠道发布 → 独立验收”的拒审修复分支。本增量使用现有控制面、Git、方案生成、独立质量和发布连接器。主线程顺序实施，不提交、不推送、不操作真实渠道或生产。

首批支持需要重新构建的修复。纯商店资料补交仍应显示为待处理，不能靠重置旧候选或修改状态宣称完成；该路径需要连接器支持准确原操作下的资料修订，另行验收。

## 现有缺口

当前渠道能记录 rejected 并停止轮询，但拒审原因不进入后续规划，修复版本与原拒审没有闭环关系。旧状态机允许 rejected → ready/submitting，容易在原审批下再次提交相同有问题的制品。

## 方案

采用权威 `release_issue` 资源。每个候选/渠道首次进入 rejected 时，在同一事务创建一条问题，冻结原需求版本、候选 binding、包 ID/摘要、仓库/提交、外部版本和拒审观察。候选目标保存 issue ID；重放同一任务不产生第二条。

有权限的人通过 `release_issues.triage` 确认修复要求。输入包含 issue ID、期望资源版本、source binding、幂等键和说明，策略固定为 new-build。Agent 可以阅读并据此提出方案，不能代替人确认修复要求或关闭问题。

所有当前仍属必选目标的未解决拒审自动进入手工/模型方案快照；未确认的问题先阻塞方案提交。快照只包含稳定来源和确认内容，不包含任务进度。方案批准及模型结果采纳复查快照，新增拒审、需求变化或修复要求改动会使旧结果不可采用。需求变化不伪造问题已解决；已移除渠道保留历史问题但不阻塞当前范围。

候选从当前批准方案继承问题快照并计入 binding。每个关联渠道要求同仓库、原提交的严格后继、新包字节及当前需求版本下的独立验证。原候选不允许再次 ready/submitting，即使先 halted 或核对也不能绕过。新的候选仍须独立人工发布审批。

只有新候选对应渠道通过独立 publication 验收，平台才自动将问题标记 resolved，记录新候选/包/审批 binding/验收证据。发布 API 成功、提审、published 观察及整体其他渠道已通过均不能代替该验收。没有公开 close/resolve 命令。

## 实现边界

- `internal/platform/release_issues.go`：来源冻结、人工确认、来源/快照校验和完成绑定。
- `internal/platform/release_issue_plans.go`：规划快照及候选门槛，复用现有对象与事务，不新增表。
- 现有 goals/plan_generation/releases/channels/tasks：仅增加必要钩子，保持无拒审项目的原绑定格式。
- 工作台发布页展示问题、来源、修复要求和实际解决版本；方案页展示被冻结的拒审输入。
- HTTP 复用命令及 workspace；MCP 的方案工具接收相同规划上下文，人工确认不开放为 Agent 工具。

## 验收

先通过真实服务测试复现“拒审无问题记录”和旧候选重提漏洞，再实施。覆盖人工/Worker 拒审、重复完成、权限/撤权、乐观并发、幂等键冲突、规划输入变化、跨项目/错误来源、旧包/同字节/非后继提交拒绝、旧验证不能接受新包、审批独立性、发布观察不关闭和独立验收关闭。以隔离 HTTP/Git/Worker 流程实际执行修复与测试；浏览器检查桌面/移动交互；PostgreSQL 检查两连接竞争和备份恢复。全部真实商店、签名和设备验收保持其实际状态。
