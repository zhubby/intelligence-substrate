# 运行事件与监测失联闭环

本增量执行已批准产品规划中的运行监测、权限治理和故障恢复要求，延续现有 runtime/incident 资源及发布工作台。原 P3 与整体产品目标继续保持未完成。

## 产品行为

- 控制面在启动时及每 15 秒扫描活动部署。最新信号到期（90 秒），或首次激活 90 秒仍未收到信号时，持久创建 `monitor_signal_lost` 事件。失联只说明无法观察，不推断应用已停止。
- 同一项目、目标、应用、节点、事件类型最多一个未关闭事件。重复扫描、平台重启和多个控制面客户端不重复创建。新激活不自动消除同应用的故障事件。
- 保留连续三次失败打开 `application_unhealthy`、连续两次成功关闭的语义。旧的无类型 incident 视为应用故障。信号中断与应用故障可以同时存在，互不替代。
- 一个新的、有效的可信节点报告关闭信号失联事件，无论该报告健康与否。抵达时已超过90秒信号有效期的报告必须拒绝，不能沿用旧的2分钟接收窗口伪造恢复。中断后的样本重新计连续次数；报告序号和检查时间均不得倒退。报告中发现已经发生的信号空窗时，记录已恢复的失联事件，不补造历史健康样本。
- release/quality/owner 人员通过 `runtime.incident.acknowledge` 确认接手，填写处理说明。确认操作使用幂等键，只能首次接手未关闭事件；不会关闭事件、改变部署健康、降低验收或授权回滚。Agent/worker、viewer、跨项目和已失权身份不能接手。
- 事件保留触发部署、触发序号、信号截止时间、接手人/时间/说明、恢复时间/原因/部署与报告序号；打开和关闭记录独立审计事件。历史记录可在工作台展开。

## 实现边界

`runtime_incidents.go` 集中管理事务内的事件匹配、创建、恢复和接手。所有状态使用现有 Store.Update 串行事务与 PostgreSQL advisory lock，不新增数据库表。系统扫描不暴露给 Agent 作为命令。API/MCP 仍走同一业务授权路径。

`cmd/platform` 启动独立于 worker 的定时扫描并在关闭时取消、等待退出；扫描错误记录服务日志。控制面自身中断时无法告警，恢复后按保存的时间重新判断。

工作台沿用现有浅色表面、绿色强调色和共享 Form/Modal/Button。活动事件先展示类型、开始时间与接手状态，再提供接手动作；已恢复记录折叠展示。表单使用现有保存中/错误反馈、焦点与 Escape 交互，手机宽度允许换行。应用运行验收和回滚区域继续使用现有权限。

不发送邮件/外部消息，不新增任意探测 URL、自动回滚、SLO 声明或完整基础设施监控。本增量不能代替进程、数据库、磁盘/卷、证书与公网独立监控。

## 验收

1. 使用真实 SQLite 事务验证首次等待、到期、失联去重、重启、应用故障共存、报告恢复、序号/时间倒退拒绝、换版不伪造恢复和旧事件兼容。
2. 使用两个 PostgreSQL 客户端并发扫描与接手，证明只有一个活动事件/首次接手结果，审计和幂等历史可备份恢复。
3. 使用 HTTP 会话/令牌验证接手、未授权/跨项目拒绝；浏览器桌面与手机验证表单、必填说明、Escape/焦点、恢复历史与布局。
4. 使用独立平台进程和数据库验证启动/周期扫描、重启持续性与恢复，保留原 18080 预览、261 个暂存条目和既有输出。
