# 验收标准、制品与证据追溯

在“目标与需求 → 验收追溯”选择当前或历史需求版本，可查看每项标准在每个必选端的证据覆盖、制品和独立验证来源，以及候选版本的实际发布状态。

## 如何使用

1. 先核对需求版本、验收方法和必选端；未批准基线不能计入当前验收。
2. 按标准查看缺口，进入相应制品核对仓库、完整提交、包摘要、构建执行及独立验证记录。
3. 下载通过完整性核验的报告。日志型策略若没有报告附件，会明确显示“仅有执行记录，未附报告”。
4. 分别核对目标环境和候选状态。标准证据齐备后，仍需发布质量策略、人工批准、实际发布及独立渠道验证。
5. 工作区刷新或点击“刷新追溯”会重新核验；读取失败不沿用旧报告，切换目标或版本后旧响应不能覆盖新页面。

一个标准可能由多个候选包分别验证。覆盖计数只表示每个“标准 × 必选端”至少有一个准确包具备匹配的独立证据，不能把来自不同包的结果拼成一个已通过的发布候选。候选必须通过其准确制品集合的既有发布门槛。

## 数据与判定

| 信息 | 依据与边界 |
|---|---|
| 需求版本 | 已持久化的 requirement 快照及其 Resource.Revision；不是当前目标中的同名标准 |
| 标准覆盖 | 当前已批准需求、准确包 ID/摘要/提交/目标/版本、相同标准 ID 与方法、独立验证主体和有效通过记录 |
| 包完整性 | 本地实际包的 SHA-256 与大小；必要签名绑定单独校验，源码仓库与准确 Git 提交另行核验 |
| 人工报告 | 同项目、目标、需求、仓库、提交和端的 report 制品，重新读取真实字节；不自动解释其业务内容 |
| 自动报告或日志 | 已配置流水线版本、准确工作项与原始成功执行、可信质量节点；配置报告路径时必须有准确报告附件 |
| 构建来源 | 与包匹配的成功构建执行及方案批准；人工上传没有构建记录时明确显示，不能套用当前方案 |
| 设计来源 | 实际构建方案批准中冻结设计的 ID/摘要与原型 ID；该关联不证明原型本身已通过业务验收 |
| 目标环境 | 标准覆盖之外，按浏览器、桌面系统或移动真机的现有独立门槛判断；模拟器不会计作真机 |
| 发布质量校验 | 复用现有 releaseGate，返回其首项阻塞；通过校验不表示已经批准或发布 |
| 渠道状态 | 保留原候选每个渠道的真实保存状态和外部标识；提审、等待审核、已发布、已验证分别展示 |

本报告描述标准与被测包的证据关系，不推断文件或函数级实现覆盖，不自动证明需求满足程度。质量配方、测试断言、人工验收内容和真机范围仍需企业验证。

## 只读 API 与 MCP

```http
GET /api/v1/projects/{projectId}/acceptance-trace?goalId={goalId}
GET /api/v1/projects/{projectId}/acceptance-trace?goalId={goalId}&revision=1
```

省略 revision 使用当前需求版本，显式版本必须是唯一的正整数。目标必填；不存在的快照返回 404，格式无效返回 400，跨项目或撤销成员权限返回 403。

MCP `/mcp` 的 `acceptance_trace` 接收 `projectId,goalId,revision?`。revision 为正整数，结果保存在 `result.structuredContent.resource`；同 REST 共用事务内授权与推导逻辑。人类只读成员与限定项目 Agent 可读取，仍须通过现行身份、成员及委托凭据检查。

响应由显式字段组成，包含 criteria、artifacts、evidence、releases 及它们的 ID；不返回任意 run/task 数据、租约、工具原始结果或模型内容。报告不新增业务对象或审计事件。需要核对完整资源时使用原有授权读取接口。

## 历史与失效

需求改版后，历史视图使用原快照的标准、方法和目标。现有失效流程会将部分记录状态改为 stale，报告保留该保存状态，不恢复或推测失效前的“通过”或“已发布”。历史包与报告仍可核对字节，但不能计入当前标准覆盖或发布权限。

同需求下更换批准方案，构建来源仍指向原实际方案。当前候选能否继续发布由现有活动方案、质量策略和绑定校验决定，不由界面覆盖数量决定。

## 验证与部署边界

代码回归覆盖当前/历史版本、真实文件篡改、错误绑定、生产者自验、日志型原执行缺失、权限撤销与 REST/MCP 对等读取；独立 PostgreSQL 用例竞争读取与改版并实际归档恢复。浏览器样本通过 HTTP 提交合成 Worker 完成，用于验证界面/API；既有 Worker 集成测试另外执行真实命令。

派生读取会访问数据库、Git 与制品存储，并计算实际摘要。大规模项目需要在保持准确绑定与失效语义的前提下测量 I/O 和容量；本增量没有声称验证企业规模性能。

本地验证不替代真实模型效果、原生端/真机、企业身份、签名与商店/生产交付。原有预览不会自动更新。隔离工作台可通过 `python3 scripts/verify-workbench.py --suite acceptance-trace` 复验，所有临时状态和构建进入 work/。
