# 渠道拒审回流与修复交付

渠道拒审后，平台保留准确来源，要求有权限的人确认修复要求，再将问题纳入新的方案、构建、独立验证及发布批准。对应新版本完成该渠道的独立发布验收后，问题才会解决。

需要改变应用行为时使用 **新构建**策略 `new-build`。App Store 仅改文字/HTTPS链接时，可选择 `store-text`，进入[原构建资料修订](store-material-remediation.md)，由独立新批准授权；保留原候选和其他端。截图更换、其他渠道资料补交仍待接入与实际验收。

## 从拒审到修复

1. 可信发布节点查询到准确版本 `rejected`，或发布负责人依据渠道实际结果记录拒审。平台在同一事务创建 `release_issue`，候选目标保存 `rejectionIssueId`。重复完成同一执行只确认原结果。
2. 在“构建与发布”查看拒审问题，核查原版本、外部标识、原因、提交及包摘要。渠道原因属于不可信外部内容，不能授予 Agent 新权限或作为工具指令。
3. 产品、架构或发布负责人在当前需求已经批准后，点击“确认修复要求”。明确需改变的行为和应补充的验证。需求版本变化时须重新确认；调整已确认要求会使旧规划输入与候选门槛不再匹配。
4. 在“目标与需求”的交付方案中重新规划。所有当前必选渠道的未解决问题自动进入人工及模型方案；无需手工复制。未确认的问题阻塞规划，Agent 可阅读及提案，人工架构批准仍是单独步骤。
5. 在原仓库、原拒审提交的后继上实现修复，构建新字节的包。为当前需求和新包运行独立质量验证，并补齐对应目标环境证据。更换仓库、重新上传同字节或复用旧报告均不满足门槛。
6. 创建新的候选版本，核对冻结的问题与修复要求，由独立发布负责人重新批准。可信发布服务使用这个新批准执行；原拒审候选不能再次变为 `ready` 或 `submitting`，先暂停或核对也不能绕过。
7. 跟踪新版本的实际渠道结果。上传、提审和 `published` 观察都保留问题未解决。独立质量人员核验准确外部版本、制品、当前需求及目标环境，提交 `publication` 证据并执行 `releases.verify`；平台随该渠道 `verified` 原子解决匹配问题。

新方案批准会使旧候选失效；旧候选中的拒审问题及来源仍保留。问题解决与整体交付分别记录：所有必选目标完成独立发布验收，整体版本才是 `delivered`。

## 对象与绑定

| 字段 | 含义 |
|---|---|
| `release_issue.data.source` | 原候选 ID/binding、需求版本、方案 ID、目标、包 ID/摘要、仓库/提交、外部 ID、原因及准确拒审观察 |
| `data.binding` | 冻结来源的 SHA256；人工确认须携带它 |
| `Resource.revision` | 修复决定的乐观并发版本；每次确认递增 |
| `data.requirementRevision` | 原拒审的历史需求版本，保持来源含义 |
| `data.triage` / `triageBinding` | 人工当前确认、确认时的需求版本、说明、策略、人员和时间及摘要 |
| `data.decisions` | 不覆盖的确认历史 |
| `plan.data.releaseIssues` | 控制面派生的稳定来源和确认快照，参与方案及批准绑定 |
| `release.data.releaseIssues` | 从当前批准方案继承的未解决问题，参与新候选和发布批准绑定 |
| `data.resolution` | 替代候选/binding、包 ID/摘要、提交、独立发布证据 ID、外部 ID、验收人和解决时间 |

新构建问题状态为 `open → triaged → planned → resolved`；`store-text` 在 triaged 后进入独立资料提案/批准，完成当前资料的独立发布验收后 resolved，不进入新构建规划。调整修复要求回到 `triaged`，需要重新规划；需求改变时，界面显示待确认。移出当前范围的渠道问题保留为历史，不阻塞无关范围，也不会因此显示为解决。重新纳入后仍需按当前需求确认。

无拒审问题的项目保留既有候选绑定格式。单目标同时未解决的问题超过 100 条时阻塞规划，由负责人整理范围。

## HTTP 与 Agent 接入

读取授权项目 workspace 或 `GET /api/v1/resources/{id}` 可获得问题。人工会话通过下列命令确认；会话写请求仍需 `X-CSRF-Token`。

```http
POST /api/v1/commands/release_issues.triage
Content-Type: application/json

{
  "id": "release_issue_...",
  "expectedRevision": 1,
  "expectedBinding": "准确问题来源的64位摘要",
  "key": "此次人工确认的稳定请求标识",
  "strategy": "new-build",
  "instructions": "在提交反馈前要求明确隐私同意；新包须独立验证未同意、拒绝及正常同意三种情况。"
}
```

仅接受以上字段。`expectedRevision` 使用刚读取的资源版本，`expectedBinding` 使用 `data.binding`。相同人员、问题、key 和内容重放返回当前问题，不新增决定；同 key 不同内容或过期版本返回 `409`。发生权限撤销时，旧凭据及缓存身份不能继续操作。`403` 表示人工/权限约束；缺参数、错误策略及不支持字段返回 `422`。

MCP 的 `get_resource`、`project_workspace` 及既有规划入口使用同样的读取与提案权限；`release_issues.triage` 不向 Agent 开放。`releaseIssues` 是控制面保留字段，规划/候选请求不能自行填写。没有公开 `release_issues.close/resolve` 命令。

模型生成开始时持久保存问题快照，结果采纳与人工方案批准都复核当前来源、修复要求和需求版本。新增拒审、来源损坏、决定修改或需求改变会拒绝旧结果；已产生的模型费用保持原核算规则。

## 故障与核对

- 拒审来源缺失、制品字节损坏或绑定不匹配时保持阻塞，先检查原候选、归档和审计；不要通过编辑数据库补成功状态。
- 新包质量失败按现有缺陷修复流程回流；发布门槛持续检查准确需求、方案、质量策略和证据。
- 渠道超时或外部结果不明沿用[发布核对流程](releases.md#查询未知结果与恢复)，不能当作拒审，更不能盲重提。已拒审旧候选不会因核对解除重提限制。
- 需求变更后，重新批准需求并确认修复要求。新候选仍须从原拒审源码的后继产生；移除渠道只改变当前范围，不改写历史结果。
- 控制面备份包含问题、决定、幂等、方案/候选、审计及源码/制品。恢复后按[运行手册](operations.md)核验完整性；签名、分发与商店节点仍需分别备份。恢复数据库不证明外部渠道已恢复。

## 验证边界

自动测试包含 SQLite/专用 PostgreSQL 并发、HTTP/MCP 权限、Git 后继、新包、独立 QA、重新批准及验收关闭。真实 Worker 样本实际执行 Python 修复、构建及对下载包的测试；发布程序使用明确的本地模拟渠道，浏览器环境和 publication 声明仅用于控制契约。因此样本中的 `delivered` 不能证明真实公开发布。

桌面及移动宽度的工作台浏览器验证只证明操作与展示。正式商店、签名、真机、目标系统安装及生产业务验收须分别提供实际证据，完整 P3 仍以两个应用所有声明必选端和渠道的正式交付为准。
