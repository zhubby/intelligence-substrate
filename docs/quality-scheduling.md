# 首次独立质量验证的自动调度

质量负责人可以把受保护测试策略绑定到已批准的需求版本及活动方案。可信质量节点轮询时，控制面为该方案的成功构建制品创建独立验证工作项。首次验证不再需要逐制品手动启动；需求、方案及正式发布仍沿用人工批准。

## 工作台操作

1. 批准需求基线与交付方案，注册 `quality + test + trustedQuality=true` 的独立节点，选择与策略一致的执行系统。
2. 在“质量与证据”建立真正检查制品内容或运行行为的验证策略。策略定义命令、执行系统、方法及验证环境。
3. 在策略行选择“自动绑定”，确认当前目标、基线、必选端、业务标准和单次预算。表单固定打开时的目标、版本和方案，不能随页面切换改变提交对象。
4. 开发节点成功构建后，独立质量节点的下一次轮询会创建并领取验证任务。页面展示绑定、调度记录、准确提交、日志和阻塞原因。
5. 需要更换策略或预算时，填写原因撤销旧绑定，再用新请求键绑定。撤销取消尚未结束的关联验证，历史证据与已发生费用保留。

没有匹配质量节点时保留等待状态，控制面不会启动另一套常驻执行资源。绑定也处理当前方案中已存在的成功构建；恢复后的轮询使用同一去重历史。页面的“已绑定”或“自动验证已启用”仅表示策略生效，具体制品结果以调度对应的工作项为准。

## API 与权限

使用 `POST /api/v1/commands/quality.bind`：

```json
{
  "goalId": "goal_example",
  "expectedRequirementRevision": 3,
  "expectedPlanId": "plan_example",
  "pipelineId": "pipeline_example",
  "target": "web",
  "criteria": ["criterion_example"],
  "budgetCents": 100,
  "key": "quality-policy-attempt-001"
}
```

所有字段都需明确给出，不接受额外字段或开发请求提供的测试命令。`budgetCents` 为非负整数美分，不能超过目标总预算。标准ID不得重复，服务器按ID排序；每项标准的方法必须与策略一致。空数组仅用于验证准确的目标环境，普通CI或模拟器策略不能用空标准绑定。目标必须属于当前需求基线。

撤销使用 `POST /api/v1/commands/quality.revoke`：

```json
{"id":"quality_policy_example","reason":"复核新的浏览器验收策略","key":"revoke-attempt-001"}
```

两条命令仅供当前有效的人类 `quality/owner` 使用，Agent与Worker不能调用，MCP不暴露。Cookie写请求要求Origin及CSRF；委托凭据与会话权限在事务内重新检查。同一操作者、目标与key的相同请求返回原对象当前状态，换输入复用key返回409。相同活动绑定不能通过换key重复创建；每目标最多32条活动绑定、200条历史绑定。

原 `pipelines.run` 仍可供人类质量人员手动验证。手动验证没有自动策略来源，不能代替已绑定策略要求的准确证据。

## 调度来源与持久对象

`quality_policy` 保存需求版本、活动方案及其批准摘要、验收基线摘要、策略ID/版本/内容摘要、方法、系统、环境、目标、标准、预算、绑定人及自身摘要。需求或活动方案变化会使旧绑定失效，需要质量负责人重新确认；策略内容漂移也会拒绝后续执行。

只有以下来源可以自动调度：

- 当前项目、需求版本和活动方案中的成功 `build` 工作项及成功执行记录。
- 该执行结果明确返回的 `package` 制品，目标与构建任务一致。
- 制品的执行、生产者、仓库、提交与构建结果一致，实际存储字节通过摘要校验。

任意人工上传、尚未完成的构建、失败构建或仅自报的任务状态不满足这些条件。

`quality_dispatch` 按 `(policyId, artifactId)` 在同一SQL事务持久去重，保存策略、制品摘要、提交、仓库、构建执行/任务和验证工作项。每次匹配节点轮询最多新建64条调度。`scheduled` 表示已经建立工作项，排队、运行、失败或通过由该工作项决定；策略或字节不安全时保存 `blocked` 及原因。

验证工作项固定为独立 `quality/test`，保留 `qualityPolicyId`、`qualityPolicyDigest`、`qualityPipelineDigest` 与 `qualityDispatchId`。外部方案不能自行填写这些字段，开发Agent不能修改此类任务依赖、取消或重试。普通已批准开发任务仍可按原边界调整依赖。

## 执行、修复与预算

领取、结果完成均重新验证当前策略、调度和准确制品。节点信任、测试能力或执行系统变化后，旧租约结果被拒绝，包括失败结果，不能借此触发修复。可信Worker获取测试策略后还会核对内容摘要，避免同版本但内容不同的命令进入工具。

策略可通过 `reportPath` 要求实际命令产生报告。该字段属于策略内容摘要，不能由开发任务覆盖。Worker收集本次报告，控制面按原run绑定准确被测制品；成功缺报告阻塞，失败报告保留，完成及候选门槛均校验来源/实际字节。证据和自动验证记录可下载准确报告，详见[报告及真实参考验收](reference-quality.md)。

实际命令失败沿用已有缺陷链：按批准开发模板修复、重新构建，再由原策略复测，最多两轮自动修复。修复后的新制品有新的调度，原策略已经创建的复测任务会被复用；其他活动策略各自调度，不为同一策略/制品双派。没有合法修复模板或超过限制时显示阻塞。

受控签名包采用 unsigned→新签名→原策略复验的专用延续，保持批准身份和原操作历史；覆盖 [Android](android-signing-repair.md) 及 [iOS/macOS/Windows](native-signing-repair.md)。质量中心的缺陷详情显示每一步真实状态。签名未知结果不属于可自动修复的质量失败。

领取时预留单次验证预算，运行完成沿用已有费用与预留释放规则；这不是云节点、真机或人工的自动账单计量。实际基础设施费用仍由负责人通过[交付成本](delivery-costs.md)核对。目标剩余预算不足会阻塞工作项。

需要重试时，由人类质量负责人在“Agent与执行”处理原工作项，仍受次数和预算上限约束。策略漂移不能靠重试修复，需要撤销并重新绑定；没有工作项的blocked调度也需先排除根因后重新绑定。不得删除去重记录来触发重复执行。

## 发布与恢复

候选版本固定当前活动质量绑定的ID与摘要。每个相关制品都需有同策略、同提交、同制品摘要的独立通过证据，能追溯到成功执行和准确调度。普通手动流水线证据不能替代。绑定或撤销后，旧候选的批准不能继续用于新操作，需要重新创建候选和批准；历史交付事实保留。

CI、模拟器、浏览器、目标桌面系统与移动真机证据仍有不同用途。自动CI通过不能放行Web浏览器、桌面系统或移动真机门槛。平台校验来源与绑定，测试策略是否充分、物理操作是否真实仍由独立质量制度保证。

工作项、调度和幂等记录随数据库持久化与备份恢复。进程死亡不新建第二条调度；有效租约仍占用原任务，失效后按现有重试上限重新领取同一任务并形成新run，旧租约不能提交。恢复数据库不会恢复工具进程或本地测试会话。签名、商店和生产操作继续由原发布审批与可信服务控制。

## 隔离复验与验收边界

```sh
rtk proxy go test ./internal/platform ./internal/httpapi ./internal/worker -run QualityScheduling -count=1
rtk proxy npm --prefix web run test:e2e -- --suite quality-scheduling
```

设置 `IS_TEST_POSTGRES_URL` 指向专用库才会执行真实PostgreSQL并发与归档恢复测试；未设置时会明确跳过，不能称为完整SQL验收。标准浏览器运行器使用隔离服务、数据和构建目录，不覆盖已有预览的静态文件。浏览器样本通过HTTP模拟完成结果；另有真实Worker测试执行实际源码、构建、失败测试、修复及复测工具。

本增量不证明真实模型自主研发质量、移动/桌面原生签名或真机、真实商店上架及企业生产验收。整体P3仍需两项不同业务在全部声明必选端/渠道的正式交付。
