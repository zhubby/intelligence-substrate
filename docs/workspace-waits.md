# 开发与设计工作区的协作等待

开发或设计 Agent 遇到需要明确答复的问题时，可以保存当前工作区、释放执行节点，并在准确回复到达后由可用节点继续。原始需求、批准方案、源码提交、目标分支和预算保持绑定。工作区记录不是合入、构建、设计批准或测试通过证明。

## 工作流程

1. 无固定 command 的 code/design 工作项通过 message 动作向指定协作者发送 request、clarification 或 review。
2. 模型返回现有 wait 动作及准确 requestMessageId、原因、摘要和等待时间。可信 Worker 选择源码、写入并同步本机私有 tar，再上传到控制面。
3. 控制面把经过校验的完整归档保存为独立 `workspace_checkpoint`，随后 tasks.wait 在一个事务中绑定其 ID/摘要、保存等待、挂起 run 并删除租约。等待时不占活动 Worker 名额。
4. 只有原指定协作者、准确因果请求及工作项的回复才能写入持久收件并唤醒任务。可在工作项详情中由指定人类回复；负责人不能冒充其他接收人。
5. 新 Worker 获取原始固定源码和准确工作区，完整替换临时目录，开始全新模型会话。完成开发时仍经过原源码提交、评审及独立质量路径；完成设计只生成待选提案。

## 保存内容与边界

- 完整归档最多 64 MiB（含 tar 元数据）、20,000 条目，沿用源码安全路径规则。拒绝链接、设备、路径逃逸、`.git`、控制器制品路径、重复及大小写/Unicode 冲突路径和非零附加内容。
- 保留二进制、删除、执行权限和原跟踪路径；新增文件遵循 Git ignore。恢复过的文件加入跟踪集合，后续 ignore 变化不会悄悄丢弃这些文件。Windows 通过模式记录保留归档执行位；这不代替 Windows 节点实测。
- 设计工作区相对原始提交只能新增/修改非可执行 HTML/HTM，单文件 1 B–2 MiB。原始其他文件必须完整保留；可执行源码不能被设计操作覆盖。
- 只保存选定文件；依赖缓存、工具会话、运行/后台进程、外部副作用、旧模型对话及隐藏推理不恢复，命令不自动回放。分析任务仍拒绝在执行命令后等待。
- 不是通用进程检查点。未落盘或未上传的文件不具备跨节点恢复保证；磁盘丢失仍需节点/控制面各自备份。

## 源码、集成与治理

原 code sourceBinding、基础提交和 expectedHead 不改变。目标分支变化时，继续任务被阻塞，需要核对或批准新的工作项；不能以“恢复”为由覆盖其他写入。工作区保存不创建 source_commit/change，也不能作为依赖源码生产者。

集成任务保存控制面准备记录以及当时准确的部分冲突决定。本等待机制只把当前有效等待所绑定的工作区及决定带入新 run；普通中断的确认进度另按[Agent 持久进度](agent-progress.md)核对恢复，不能继承未确认的决定。成功进入显式等待后清空普通进度指针，后续先以本次等待检查点继续。保存后修改决定或提交源码，均不能沿用原工作区等待。最终提交仍逐项核对全部冲突的字节、删除、模式及冲突标记；恢复后编辑已处理路径需要重新 resolve。

每工作项最多三次等待、累计 24 步。费用和活动执行时间累计扣减原任务包络，等待时间不占活动 timeout。费用未明、预算用尽、身份/角色/能力撤销、需求/方案/配方变化或取消均不能突破原约束。消息和工作摘要始终是不可信协作数据，不能批准需求或发布。

## 接口

`POST /api/v1/runs/{id}/checkpoint` 使用 Worker Bearer token、`Content-Type: application/x-tar`、唯一 `X-IS-Checkpoint` 头；头为标准 base64 编码 JSON，编码后最多 8 KiB，仅含三个字符串：

```json
{"leaseToken":"<current-run-lease>","repositoryId":"repository_...","commit":"<original-full-sha>"}
```

不接受查询参数、未知/重复 JSON 字段、空缺或非字符串。上传前及注册事务内都复核当前授权、工作项、租约/截止、源码/分支和预算。每 run 仅保存一份不可变工作区；同一绑定和完整原始字节重放返回原资源，不同内容冲突。资源与幂等记录、成功审计同事务提交，不保存租约令牌。

code/design 的 `tasks.wait` 在原参数上增加必填 `checkpointId`。控制面派发的 `messageContinuation` 带准确 checkpointId/checkpointDigest。自定义 Worker 通过 `GET /api/v1/runs/{newRunId}/checkpoint`，携带当前 token 和唯一 `X-IS-Lease` 头下载；仅允许该活动执行的权威继续记录，返回 no-store tar。不能按任意检查点 ID或人类会话下载；普通制品 content API 也不接受该资源。

## 失败、恢复与运维

上传响应丢失时 Worker 最多准确重放三次，不重新调用模型。等待提交通过原有落盘 journal 重放。成功确认等待后清理本机 `stateDir/workspace_<runId>.tar`；确认前或结果不明确时保留原字节供操作员核对。挂起失败不会走中断源码分支登记，以免把等待误当作源码采用。

上传结果不明确且无法挂起时，工作项明确阻塞，平台可能已有 saved 记录，本机 tar 仍保留；不会从旧租约自动继续或自动导入该 tar。操作员核对 run、工作区摘要和等待记录后，在当前授权的新工作中接管；不要删除唯一副本或手改业务数据库。旧节点凭据失效时重新签发，不能延长原租约。

工作区 CAS 纳入控制面现有 artifacts 私有目录的备份；恢复完整性检查会校验工作区的实际摘要与大小，损坏时拒绝恢复。节点上的未确认 tar 由节点状态备份单独保护。工作台保留等待历史、准确源码提交、文件数、摘要及已记录集成决定数；这些展示不代替实际恢复或质量验收。

## 验证方法

Go 测试使用实际 HTTP、Git、文件工具、SQL 和替换 Worker；本地确定性 OpenAI 兼容提供方验证代码的两次等待及逐笔累计费用。包括二进制/删除/执行权限、后续 ignore 变化、HTML 原型、部分集成决定、未重新 resolve 的拒绝、三次上限、早到回复、丢失响应和审计回滚。PostgreSQL 双连接并发重放后，在仍等待时实际备份、恢复 SQLite，再由替代节点取得准确工作区。

浏览器以真实 API 构造工作区等待，验证桌面/390px历史、指定人回复、键盘、滚动、Escape 和焦点；实际模型循环由 Go 场景独立验证。当前不把这些确定性测试当作真实大模型业务质量、Windows 本机、物理设备或正式发布证据。精确结果见[验收记录](validation.md)。
