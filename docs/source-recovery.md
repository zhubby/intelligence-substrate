# 中断源码的核对与人工接管

源码已保存，不等于执行已完成。快照可能在 Git 更新后、SQL 确认前中断；也可能已经确认，但节点未报告完成就失去租约。原租约仍有效时精确重放原请求；原租约失效、进程失败或节点停用后，由项目负责人核对固定候选，决定采用或停止采用。

## Agent 尚未 finish 的源码

代码 Agent 因模型错误、预算停止、显式 blocked、取消或步骤耗尽而受控返回时，Worker 对比实际源码与领取输入。文件有变化时，先在自己的 `stateDir` 下创建私有 `.stopped-source-*` 目录，保存 `source.tar` 和 `context.json`。源码保留现有选择规则中的工具生成字节、删除和执行权限；元数据只含项目/任务/执行、输入与输出摘要、分支和绑定来源，不包含租约、模型对话或凭据。

原上下文仍有效、且尚未发起最终源码提交时，Worker 将同一份本地 tar 通过现有受控快照接口登记为中断候选，使用原执行的幂等键和租约。原错误、日志与非零退出保留，任务进入“源码待核对”；只有人类负责人可以采用。采用后仍需实际构建和独立质量检查，不能据此批准发布。

| 结果 | 权威状态与处理 |
|---|---|
| `candidate_saved` | 平台确认了准确摘要的源码操作，可在工作台核对；不是执行成功 |
| `local_only` | 节点保留私有副本，上传未确认或原上下文已结束；没有自动导入/重放权限 |
| `sourcePreservationError` | 快照未完整保存，原错误继续保留，不能声称有可恢复副本 |
| 输入未变 / 非代码任务 | 不生成额外源码候选或本地副本 |

工作台将只有节点报告的本地保存和保存失败单独显示，并给出节点及摘要。节点无法确认上传、但平台实际已有 prepared/committed 候选时，优先展示平台“核对源码”，不会误报尚未同步。平台尚未接收的私有副本由执行节点管理员根据 `context.json` 的 runId/输入绑定与 SHA256 查找、备份和核对；不能直接标记任务成功或替换制品。

若最终源码提交已经发起，不另建第二次操作；失去回执时核对原操作。原租约或需求失效会拒绝登记，原本地副本继续保留。危险链接、路径或超过 64 MiB / 20,000 条目的源文件不会生成“已保存”声明。管理员可按企业策略备份和管理这些私有副本，平台不自动删除既有资料。

此能力仅覆盖 Worker 能够受控返回时的源码保存，不是模型会话或工具步骤检查点。kill -9、宿主失联、硬盘丢失和仍在运行的外部命令不在该保证内，不会自动重放模型或工具。AX/容器/native 执行后的源文件仍受各驱动本身的返回/隔离边界约束。

普通工具意图与最后确认文件另由[Agent 持久进度](agent-progress.md)保护。存在尚未确认的 prepared 操作时，Worker 保留该核对屏障，不进入本节的受控停止源码回退；确认进度也不等于采用源码。两种机制都不能证明原进程或外部副作用已经停止。

## 工作台

项目交付空间 → 执行记录 → 工作项的“核对源码”。弹窗显示候选完整提交、当前分支完整提交、原生产者、执行与节点状态，可以下载候选检查。已授权成员可以查看，只有项目 owner 或站点管理员的人类可以决定。

- **采用并继续**：候选仍在控制面保留引用中，实际分支包含候选，原需求、活动方案和源码绑定有效，没有活跃执行或其他已采用结果时，确认原源码产出。下游固定使用原候选，不使用后来推进的分支头。
- **停止采用**：保留候选、分支、原作者和审计，关闭此候选的采用流程。不会撤销 Git 提交，也不会复活已取消/过期的工作。继续开发前核对原绑定；目标已变化时需要新批准的工作项。
- **刷新核对状态**：读取实际分支和当前权限。检查后分支再变化，提交会被拒绝；原因输入保留，刷新并重新检查后再决定。

活跃租约不能抢占。停用节点的权限不会恢复。分支不存在或不含候选、保留引用异常、源码绑定损坏、需求/方案失效时不能采用；可用的停止采用入口只关闭候选，不修复 Git 或修改需求审批。

## 只读检查

`GET /api/v1/source-operations/{sourceOperationId}`，需要项目访问权限，返回：

| 字段 | 含义 |
|---|---|
| operation | 原 source_commit，含固定候选、仓库、分支、原作者与执行 ID |
| observedHead | 本次实际分支完整 SHA；分支不存在时为空 |
| runStatus / workerStatus / taskId | 原执行、节点状态及工作项 |
| canConfirm / canAbandon / reason | 当前身份可否决定及具体原因 |
| recovery | 已有 source_recovery 决定；有决定时两个能力均关闭 |

响应不返回原租约令牌或完整 run body。MCP 的 `inspect_source_operation {id}` 提供相同只读能力；检查结果不授权之后的写操作。

## 人工决定

`POST /api/v1/commands/sources.reconcile`，使用人类负责人的会话与 CSRF：

```json
{
  "id":"source_commit_...",
  "key":"稳定的本次核对键",
  "commit":"原候选完整 SHA",
  "observedHead":"本次观察的完整分支 SHA；不存在时为空",
  "decision":"confirm",
  "reason":"核对批准任务和准确候选后继续独立构建验证"
}
```

严格要求六个字符串字段，不接受其他字段。decision 为 `confirm` 或 `abandon`，原因非空且不超过 2000 字节，key 使用 1–96 字符 ID 规则。commit 不能任意换成新的分支头。失去响应时，同一主体使用相同 key 和完整请求重放；修改观察、原因或决定需要新 key。同一操作最多一个决定。Agent/Worker 身份无决定权限，此命令不在 MCP Agent 命令列表中。

响应为 `source_recovery`，状态 `confirmed` 或 `abandoned`。记录操作、仓库、分支、候选、观察头、原因、决定者、原生产者、task/run、需求/方案、源码绑定摘要及先前执行状态。决定与关联状态在同一 SQL 事务提交；失败不会留下半个决定。受控 Git 写入口通过现有 Store 事务锁与核对串行，核对本身不写 Git。

## 来源与后续执行

确认后 op/change 为 committed，原 change.authorId、run.workerId 不变。run 明确为 recovered（工作台“人工接管确认”），task 为 succeeded。原退出码和日志保留；没有退出码时不会添加 0，不伪造完成摘要或续发租约。先前结果与状态附在决定中，原日志留在原执行；原 Worker 无法再提交、心跳或完成。

下游重新核验 recovered 决定、原操作/身份、需求/方案、源码绑定与实际提交，不能只凭状态字样采用。集成保留原 integrationId、冲突决定摘要及全部父输入。修复任务恢复后重新安排受保护构建与独立复测，只有真实复测通过才关闭缺陷。

过期、失败或超时任务若有未完成的 prepared/committed 快照，进入“源码待核对”，记录 sourceRecoveryIds；通用 retry 被拒绝，不消耗新尝试。采用不产生预算消费、质量证据、评审或发布批准。

此流程针对新的完整源码快照端点。旧文本提交和普通 Git push 没有相同的持久候选协议；不执行未落地候选、不重放命令、不修复异常 Git 元数据。来源/过程证据不能代替业务验证。本地 Git/SQL/HTTP/Worker/浏览器验收不等同于真实模型、AX、宿主沙箱、原生应用/真机、签名或正式渠道验收。
